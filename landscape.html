终端助手的下一站，
不是更多命令。

CoCo 已经拥有可靠的本地基础设施。与 Codex、Claude Code、Pi Coding Agent 和 OpenClaw 等产品相比，真正需要补齐的是任务隔离、并行执行、开发工作流连接和可恢复性。

01 / 核心判断

CoCo 不缺一个更大的模型，缺的是模型之外的产品层。

已有护城河

本地可信运行

离线启动、内网部署、运行时完整性、保守安装与卸载，以及项目资源的 global-only 策略，构成 CoCo 最清晰的差异化。

产品基础

分支化会话与 Goal

会话树、fork、clone、resume、compaction 与持久化 `/goal` 已经适合长任务，但还缺文件级 checkpoint 和隔离工作树。

最大缺口

从单会话到任务系统

头部产品把代理扩展到后台、云端、PR、IDE、定时任务与多代理协调。OpenClaw 进一步展示了自托管网关、调度与远程节点的组合；CoCo 仍主要是用户面前的一条本地终端会话。

02 / CoCo 现状

强基础，窄表面。

已经具备

  • 终端交互、headless、JSONL RPC 与 SDK
  • 会话树、fork、clone、resume 与 compaction
  • 持久 `/goal`、步骤状态与模型 goal tool
  • 图片输入、扩展、skills 与自定义工具
  • 五个托管 provider 与自定义 provider 登录
  • 离线包、内网模型、双语与语言包
  • 运行时完整性、secret scan 与安全 guard

原生缺失

  • OS 级 sandbox 与通用权限规则
  • MCP 客户端与服务器治理
  • 原生 subagents、agent teams 与工作树调度
  • 自动文件 checkpoint 与一键 rewind
  • VS Code / JetBrains 原生扩展
  • GitHub PR、review、issue-to-PR 自动化
  • 云端后台任务、事件自动化与企业控制台

边界：CoCo 与上游 Pi 的扩展示例可实现 plan、todo、subagent、Git checkpoint 等工作流，但“可扩展实现”不等于产品原生能力；本报告按开箱即用能力计分。OpenClaw 是自托管个人代理网关，不是纯 IDE 编码代理，矩阵只比较其相交能力。

04 / CoCo 没有而参照产品有

十二个缺口，不应该十二个一起做。

01 · P0

原生沙箱

Codex、Claude Code、Gemini 与 OpenClaw 提供 OS 或容器级隔离。CoCo guard 只能分类与确认，仍以用户权限执行。

02 · P0

Checkpoint / Rewind

Claude Code 自动快照；Gemini 启用 checkpointing 后可恢复文件与对话；Aider 默认为 AI 编辑创建 Git commit。CoCo 与上游 Pi 仅有会话树和扩展示例。

03 · P0

原生工作树任务

Codex、Claude Code、Cursor 与 OpenClaw 可用 worktree 隔离修改。CoCo fork 隔离对话分支，但不隔离工作目录。

04 · P0

原生 Subagents

多个产品允许配置代理角色、模型或工具，并提供并行调度。OpenClaw 还支持后台嵌套编排；CoCo 与上游 Pi 只有示例扩展。

05 · P1

MCP 客户端

Codex、Claude Code、Gemini、Copilot、Cursor 与 OpenClaw 均原生支持 MCP。CoCo 与上游 Pi 只能经扩展自行集成。

06 · P1

GitHub 工作流

Codex、Copilot 等产品已把接收任务、代码审查、CI 修复或产出 PR 纳入 GitHub 工作流；Claude 与 Cursor 也覆盖其中部分环节。

07 · P1

IDE 原生体验

竞品可以读取 selection/open tabs、展示内联 diff、计划审批和历史。CoCo 的集成面仍是终端、RPC 与外部编辑器。

08 · P1

后台任务

用户关闭窗口后，Codex cloud、Claude web、Copilot agent 与 Cursor cloud 仍可持续执行并回传结果。

09 · P2

定时与事件触发

CoCo 已有会话级 `/loop` 定时提示，但仍要求对应会话保持运行；Codex Automations、Claude Routines、Copilot Automations 与 Cursor Automations 进一步支持持久 schedule、webhook 或 GitHub 事件。

10 · P2

远程控制

Codex、Claude 与 Cursor 都提供远程或云端任务入口；具体能否接管本地主机会因客户端、套餐和运行模式而异。

11 · P2

浏览器 / 视觉验证

部分头部产品已提供浏览器交互或视觉产物；Cursor Cloud 明确支持截图、录屏和远程桌面，形成实现后的验证线索。

12 · P2

企业治理

团队采购通常要求集中策略、身份管理、审计、可观测性、集成治理和留存控制；CoCo 尚未形成对应的管理平面。OpenClaw 虽有策略与 OTel，但官方仍定位为单操作者边界。

05 / 建议路线

先把本地代理做成可靠任务系统，再扩展到云。

Phase 10-3 个月

Safe Local Work

实现 Linux/macOS OS sandbox、统一权限规则、自动 checkpoint/rewind、worktree-backed `/goal`。这是信任与并行的共同底座。

  • workspace-write / read-only / full-access 模式
  • 命令、网络、路径三级规则
  • 每轮文件快照与安全恢复
  • Goal 分支与 worktree 生命周期绑定
Phase 23-6 个月

Connected Development

将扩展示例收敛为稳定产品能力：subagents、MCP、GitHub 与 IDE。保持本地优先，不急于自建云执行。

  • 原生 explorer / reviewer / worker agents
  • MCP server registry 与 tool approvals
  • GitHub Action、PR review 与 issue-to-branch
  • VS Code thin client，复用 RPC
Phase 36-12 个月

Optional Control Plane

提供可选、自托管优先的后台调度层，而不是复制一个封闭 SaaS。保留离线 CoCo，同时支持团队任务与审计。

  • 队列、schedule、webhook 与任务通知
  • 容器化远程 runner 和 artifact review
  • 策略分发、OTel 与审计事件
  • 浏览器验证和移动端只读监控

06 / 不建议复制

CoCo 应该选择，不应该追平所有 checkbox。

不要先做大型桌面壳

RPC 和 VS Code thin client 足以验证 IDE 需求；桌面多窗格不是安全执行和任务隔离的前置条件。

不要先做封闭云

CoCo 的优势是离线与内网。OpenClaw 证明自托管网关与远程节点可形成另一条路径；CoCo 应优先采用开放 runner 协议。

不要把扩展当原生能力

高价值示例应晋升为有版本、测试、权限和兼容承诺的产品模块，不能只在文档中声称“可以扩展实现”。

07 / 方法与来源

只采用第一方资料，结论可复核。

调研日期为 2026-08-09。能力会随版本、地区、套餐和灰度发布变化；“未发现”不等于产品永远没有。CoCo 能力来自仓库代码与文档审计；Pi 与 OpenClaw 按其官方仓库和文档计分。
